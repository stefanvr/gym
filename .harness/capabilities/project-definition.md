# Project Definition

Coordinates the path from a bounded Goal to implementation-ready Project authority without taking over Domain, App, Style, Tech, or Build ownership.

## Purpose

Make the intended change clear enough to implement under the selected Project model.

## Skills

- `understand` — targeted repository analysis when current context is insufficient
- `define` — resolve the Goal into implementation-ready authority using relevant reasoning capabilities and methods
- `document` — optionally persist useful knowledge from completed Goal work or an explicitly published Discovery finding in native docs or projected Harness Spec form

## Shared contracts and mechanisms

- Project Authority Target Contract
- Authority Orchestrator Contract
- Method Pack Contract
- Change Impact
- Grill
- Goals and Decisions

## Model behavior

Under `spec`, Define coordinates changes into stable Spec authority through Domain/App/Style/Tech owners.

Under `repository-native`, Define coordinates the same reasoning into one transient Goal Spec. Understand may inspect the repository before or during Goal definition. Document is optional except where an existing native authoritative artifact must change to remain truthful. Discovery may also route an explicitly selected non-authoritative finding here for durable project documentation; Discovery itself owns no archive.

## Invariants

- understanding is targeted, not repository archaeology by default
- activated methods are selected for fit, not executed as mandatory ceremonies
- the definition phase ends before consequential implementation decisions are left implicit
- Build consumes Project authority; it does not silently author it
- optional documentation never creates a competing authority system
