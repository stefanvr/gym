# Harness 17 Architecture Map

This file is a non-authoritative development map for the current Harness architecture. Operational rules live in their owning Workflow, model, contract, Guide, skill, or runtime document.

## Shape

```text
Harness kernel
├── Workflow / Lifecycle / Guides / contracts
├── deterministic runtime kernel
├── checker + Assurance infrastructure
├── selected Project model
│   └── Spec: explicit stable-scope topology
├── selected Collaboration model
│   ├── single-user
│   └── cooperative multi-user
└── optional method packs
```

## Runtime ownership

```text
harness.py              CLI only
   ├── kernel.py        repository + lifecycle mechanics
   ├── project_model.py Project-model mechanics
   ├── collaboration_model.py
   │                    collaboration mechanics
   └── checker.py       deterministic checks + Assurance
```

Keep model mechanics out of the kernel. A kernel lifecycle command may cross into the selected Collaboration model only through an explicit integration hook where collaboration state changes whether a landing is mechanically valid.

## Context budget

Normal session startup loads Workflow, active composition, and Routing. Load model definitions, Guides, skills, methods, knowledge, Assurance material, and vocabularies only when the current concern calls for them.

Prefer local definitions in the owning document over globally adding terms to the working vocabulary. Add a glossary term only when it is reused across boundaries and a shared definition prevents ambiguity.

## Design tests

A Harness change should preserve these questions:

- Can lifecycle mechanics remain meaningful without knowing Spec file layout?
- Can Project-model topology evolve without changing landing semantics?
- Can Collaboration mechanics evolve without changing Project authority ownership?
- Can the checker inspect every layer without becoming runtime authority for that layer?
- Can a new session reconstruct enough context without loading the full Harness surface?
