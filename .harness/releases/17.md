# Harness 17 — Modular Runtime and Reduced Context

Harness 17 is a standalone Harness distribution with one current architecture, one current vocabulary surface, and one deterministic runtime layout.

## Runtime architecture

The deterministic runtime is split by ownership:

| Module | Owns |
|---|---|
| `runtime/kernel.py` | process/Git facts, repository lifecycle state, approvals, landing, abandonment, recovery, guarded mutations |
| `runtime/project_model.py` | active Project-model lookup and Spec topology mechanics |
| `runtime/collaboration_model.py` | active Collaboration-model lookup, actor state, cooperative handoff mechanics |
| `runtime/checker.py` | structural checks, model-contract checks, semantic evidence validation, `check`, and `assure` |
| `runtime/harness.py` | CLI parsing, dispatch, normalized output/errors, and a small embedding/test context hook |

`harness.py` contains no lifecycle, model, or checker implementation. The kernel does not own Spec or handoff commands. Its only Collaboration-model dependency is the explicit lifecycle integration seam needed to validate and finalize cooperative landings.

`check` validates module ownership and the allowed top-level dependency graph mechanically. Owned modules use explicit imports across runtime boundaries. Assurance compilation covers the complete runtime package rather than only the CLI file.

## Project-model baseline

The Spec Project model uses explicit stable-scope topology at `doc/spec/topology.json`.

Spec topology authority is declared only by `doc/spec/topology.json`. When the topology manifest is absent, Spec topology is `unconfigured`; callers establish the manifest deliberately before topology-dependent work.

## Context loading

Session startup has three shared context anchors:

1. `workflow/WORKFLOW.md`
2. `composition/active.json`
3. `workflow/routing.md`

Everything else is loaded by the active composition and current concern through `workflow/context-manifest.yaml`. Composition design, collaboration posture, vocabularies, release material, Assurance internals, and capability-specific material are not startup context unless the current work needs them.

The context manifest is an inventory and routing map. It does not restate active composition selection. `check` enforces the exact three-file unconditional startup set.

## Vocabulary

The working vocabulary contains only terms that are cross-cutting enough to improve normal Project work. Procedure-local names stay with the procedure that owns them.

The extended vocabulary is reserved for Harness development, validation, recovery, and Assurance. It is not part of normal session startup.

This keeps the glossary from becoming a second copy of Goal, Setup, Build, or capability-specific instructions.

## Composition

The shipped Project model is `spec`.

The shipped Collaboration models are:

- `single-user`
- `cooperative-multi-user`

The shipped method packs are:

- Interview Me
- Event Storming
- Story Mapping
- Design

The active selection remains single-sourced in `composition/active.json`.

## Deterministic verification

The release gate requires:

- `python .harness/runtime/harness.py check`
- runtime regression tests
- behavior-evaluator regression tests
- behavior corpus validation

Harness Assurance remains profile-qualified. A distribution without current matching real-model semantic evidence reports `UNKNOWN`, not an inferred pass.

## Operating boundaries

Cooperative operation assumes trusted participants and one serialized integration authority. Handoff acceptance is guarded by an exact remote compare-and-swap boundary. Mainline movement outside the approved handoff base fails closed as `LANDING_BLOCKED` and requires human reconciliation.

Harness Assurance evaluates Harness behavior and evidence. It does not grade the managed Project.
